# 局域网加密决策（AES-GCM / TLS）

- 日期：2026-10-27
- 状态：**决定暂不在当前 HTTP 协议上叠加 AES-GCM**
- 关联：[安全记录](README.md)、[PLAN §3.6](../../../PLAN.md)

## 结论

当前不做“应用层 AES-GCM”，原因不是性能，而是**密钥分发不成立**：

```text
房间 token 通过 X-Yanlu-Room 明文 HTTP 头传输
→ 同 Wi-Fi 抓包者可直接拿到 token
→ 由 token 派生的 AES 密钥也可被同样拿到
→ 加密 payload 不能阻止抓包者解密
```

因此“AES-GCM + token 派生密钥”是假安全，不应实现。

## 三个可选方案

### 方案 A：保持明文 HTTP，限定可信局域网（当前）

- 已有：26 位随机 token、请求头、失败限速、房间隔离
- 适合：朋友内部、可信 Wi-Fi、非公共网络
- 明确不支持：公共 Wi-Fi、不可信热点、跨公网
- 成本：0；风险：同网段抓包可读行程

**当前选择。**

### 方案 B：TLS + 自签名证书 + 指纹校验

- 房主生成自签名证书，二维码/手动展示证书指纹
- 客户端首次加入校验指纹，后续 pinning
- WebView 对自签名证书的错误处理必须严格，不能简单 `proceed`
- 成本：中高；需要原生 TLS server、证书生成、WebView 信任链、指纹 UI
- 收益：真正保护传输内容与 token

### 方案 C：PAKE / ECDH 握手 + AES-GCM

- 二维码携带短码，双方用 SPAKE2/SRP 派生会话密钥
- 再做 AES-GCM；不依赖 TLS 证书
- 成本：高；需要成熟密码库与协议审计
- 收益：可抵御被动抓包和离线猜测（取决于 PAKE 设计）

## 决策

1. **M3.3b 不实现 AES-GCM。**
2. 继续使用明文 HTTP + token + 限速，但 UI/文档明确“仅可信局域网”。
3. 如果之后需要公共 Wi-Fi/更高隐私，优先做 **方案 B（TLS + 指纹）**，而不是 payload AES。
4. 不在没有 TLS/PAKE 的情况下宣称“端到端加密”。

## 验收（未来若做 TLS）

- 同 Wi-Fi 抓包看不到 token 与 Trip 明文
- 首次加入校验指纹，错误指纹拒绝连接
- 证书轮换/房主重开房间有明确提示
- WebView 不全局忽略 SSL 错误
- 仍不需要账号/云端

## 对当前计划的影响

- §7.2 的“是否 AES-GCM”关闭为：**不做，改为 TLS 方案待定**
- 公共 Wi-Fi 使用仍列为不支持
- 安全剩余项从“AES”改为“TLS/指纹（可选）”
